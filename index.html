01 / AWAL MULA MASALAH

Kenapa Web Sering Timeout & Database Tiba-Tiba Mati?

Awalnya keluhannya simpel: website PBN kadang-kadang suka timeout, muter lama, terus gak bisa dibuka. Pas kita intip log bagian dalam server pake perintah dmesg -T, ternyata ketahuan biang keroknya: kernel Linux secara berkala panik kehabisan RAM, lalu mengeksekusi aksi "pembunuhan massal" (*Out Of Memory Killer*):

LOG DMESG KERNEL LINUX BUKTI PEMBUNUHAN DATABASE
[Thu Sep 3 15:33:39 2026] Out of memory: Killed process 8130 (mariadbd) ... [Thu Sep 3 15:35:12 2026] Out of memory: Killed process 2094 (clamd) ... [Thu Sep 3 18:32:07 2026] Out of memory: Killed process 315783 (mariadbd) ... [Fri Sep 4 11:36:32 2026] Out of memory: Killed process 955576 (mariadbd) ... [Fri Sep 4 11:37:12 2026] Out of memory: Killed process 2253131 (mariadbd) ... [Fri Sep 4 11:39:20 2026] Out of memory: Killed process 2252632 (httpd) ...

Lihat baris di atas: proses mariadbd (database MariaDB) dibunuh berkali-kali. Begitu database dibunuh paksa, ya otomatis semua website WordPress di server rontok barengan. Beberapa saat kemudian sistem nge-restart MySQL lagi, makanya web sempat bisa kebuka sebentar, lalu nanti kalau RAM penuh lagi bakal mati lagi (kumat-kumatan).

[FIG. 01] KONDISI AWAL SERVER (PERINTAH TOP) KLIK UNTUK PERBESAR
Kondisi pas lagi megap-megap: Ada 949 proses numpuk di server, Netdata makan CPU sampai 123.5%, dan RAM kesedot 86.7 GB gara-gara ratusan proses PHP jalan barengan tapi gak kunjung selesai.

Dan setiap kali database MySQL mati dibunuh oleh kernel Linux tadi, pengunjung atau bot yang lagi buka website PBN langsung disambut ini:

[FIG. 02] KORBAN DATABASE MATI (ERROR ESTABLISHING DATABASE CONNECTION) KLIK UNTUK PERBESAR
Layar yang sering muncul kemarin: Begitu MariaDB dibunuh paksa oleh sistem OOM Linux, WordPress langsung gagal nyambung ke database dan menampilkan pesan error ini serempak di seluruh domain PBN.
02 / PEMBONGKARAN MASALAH

4 Biang Kerok Utama yang Bikin Server Macet

Pas aku telusuri lebih dalam, masalahnya bukan karena servernya jelek (orang sever ini bisa nampung banyak banget domain lagi kalo mau). Masalahnya ada di settingan bawaan cPanel dan CloudLinux yang kaga pas, ini dia 4 biang keroknya:

Biang Kerok Settingan Lama Kenapa Ini Bikin Masalah?
Kecepatan Disk Dicekik 1 MB/s per akun Ibarat punya SSD Samsung NVMe Gen4 yang larinya 6.800 MB/s, tapi tiap akun cuma boleh baca 1 MB/s. WordPress butuh baca puluhan file plugin, karena dicekik jadi lama banget. Akhirnya proses PHP gak kelar-kelar dan ngendap berjam-jam di RAM.
Pintu Masuk Apache Sempit MaxRequestWorkers: 50 Punya hampir 1.000 website, tapi pintu Apache cuma muat 50 orang sekaligus! Begitu 50 orang masuk, antrean langsung meluber. Pas antrean penuh (512), pengunjung baru langsung ditendang keluar (ERR_TIMED_OUT).
644 Web Mentok Limit 644 / 978 Website Gara-gara disknya dicekik, 65% website langsung jebol batas limit CloudLinux. Fitur MySQL Governor otomatis ngambek dan nyekik kueri database (mode abusers), bikin antrean web makin macet total.
Koneksi Database Minim max_connections: 151 Ini setelan default buat VPS murah seharga 50 ribuan. Dipasang di server 1.000 web, jelas pas ada 152 koneksi barengan databasenya langsung nolak kueri.
[FIG. 03] CLOUDLINUX DASHBOARD
Angka lingkaran oranye: 644 dari 978 website mentok limit barengan.
[FIG. 04] STATISTIK LIMIT CEKIKAN
Buktinya: kolom IO dipatok cuma 1 MB/s dan CPU anehnya diset 1500%.
[FIG. 05] PENYEBAB ERR_TIMED_OUT DI BROWSER ANTREAN 443 MELUBER
Kenapa muncul tampilan ini kemarin? Pas workers Apache cuma 50, antrean port 443 langsung mentok di angka 512/511. Begitu antrean penuh, Linux langsung ngebuang semua koneksi HTTPS baru yang masuk.
03 / LANGKAH PERBAIKAN

Beresin Satu Per Satu Sesuai Spek Asli Server

Kita gak cuma tambal sulam, tapi settingan server langsung kita sesuaikan sama tenaga asli prosesor AMD EPYC 32-thread dan RAM 128 GB:

1. Buang Beban Gak Guna & Bebasin 55 GB RAM
Server PBN kan isinya cuma blog WordPress buat backlink/artikel, ngapain pasang antivirus email kantor (ClamAV) sama fitur sinkronisasi kalender/file (cPanel DAV)? Begitu kedua service ini dimatikan lewat Service Manager, RAM server langsung lega dari yang tadinya sisa 41 GB melompat jadi 93 GB BEBAS!

[FIG. 06] MATIKAN CLAMAV & DAV
Hilangkan centang di ClamAV dan cPanel DAV.
[FIG. 07] HASIL RAM LEGA (FREE -H)
RAM yang nganggur langsung melompat jadi 93 GB lega!

2. Buka Kunci Kecepatan Disk Samsung NVMe di CloudLinux
Batas baca/tulis disk per akun kita naikkan dari 1 MB/s jadi 25–50 MB/s dan IOPS ke 2048–4096 lewat perintah lvectl. Sekarang WordPress bisa baca tema dan plugin secepat kilat:

PERINTAH TERMINAL SSHCLOUDLINUX LVECTL
# Buka batas default ke 50 MB/s dan 4096 IOPS lvectl set 0 --speed=100% --pmem=1024M --io=51200 --iops=4096 --maxEntryProcs=25 --nproc=150 # Update juga paket DEDICATED (CPU dinormalkan ke 100% biar gak monopoli) lvectl package-set DEDICATED --speed=100% --pmem=1024M --io=51200 --iops=4096 --maxEntryProcs=25 --nproc=150 # Terapkan langsung serempak ke semua ~978 akun lvectl apply all
[FIG. 08] SETELAN PAKET BERHASIL DIUBAH
Daftar paket di CloudLinux sudah resmi berubah, disk gak lagi dicekik di 1 MB/s.

3. Buka Pintu Masuk Apache Menjadi 750 Orang
Ini kunci utama yang bikin website langsung bisa dibuka lagi tanpa nungguin timeout: batas workers Apache kita dongkrak dari 50 jadi 750 workers lewat menu WHM Konfigurasi Global, dan batas timeout gantung diturunkan jadi 30 detik biar koneksi yang udah ditinggal kabur pengunjung langsung diputus:

[FIG. 09] KONFIGURASI GLOBAL WHM
Max Request Workers diubah ke 750 & Timeout 30 detik.
[FIG. 10] REBUILD SELESAI
Apache sukses rebuild dan restart tanpa ada error.

4. Bikin Database Kebal OOM Killer & Kasih RAM 32 GB
Biar database gak pernah dibunuh lagi sama Linux pas RAM naik mendadak, kita kasih imunisasi pake override systemd OOMScoreAdjust=-1000. Plus, kita kasih jatah RAM raksasa 32 GB buat nampung seluruh data website di dalam memori:

/etc/my.cnf.d/monster_tuning.cnfSETELAN DATABASE MARIADB
[mysqld] max_connections = 600 # Naik 4x lipat dari cuma 151 innodb_buffer_pool_size = 32G # Semua database PBN dimuat langsung di RAM innodb_buffer_pool_instances = 8 table_open_cache = 4000 open_files_limit = 65535
